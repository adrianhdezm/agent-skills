# File storage

How an app stores uploaded files: bytes in an object store, metadata in the database, one service that keeps the two in
step. These rules apply from the moment a project stores files.

## Principles

- **Bytes go to an object store; metadata goes to the database**, because a row is read whole while an object streams.
  Never file contents in a table; the `files` table holds only what is queried, and with sign-in its owner, as
  [Authorization](authorization.md) says.
- **One service owns both sides.** `FilesService` writes the object and the row together, so it uses no DAO: every
  database call is paired with an object-store call. It is a deliberate exception to one DAO per table.
- **The object goes first, and is undone if the row fails.** Upload stores the object, then inserts the row; if the
  insert throws, the service deletes the object before rethrowing, so no object is left without metadata. Delete removes
  the row, then the object, so a failure leaves at worst an orphan object, never a row whose download fails. A download
  reads the row first and fetches the object by its stored key.
- **Keys are made by the server and unique**, because a client's name can collide or carry path segments; the client's
  filename is metadata, never the key alone.
- **The server entry builds the service** with the database client and the store's client, and puts it on the app's
  context, like any capability.
- **Uploads and downloads are endpoints like any other**: authenticated, and scoped to the owner as Authorization says;
  a download sets the row's `Content-Type` and `Content-Disposition: attachment` with its filename.
- **Store configuration is the runtime's**, so no code holds a credential the platform already holds: a binding where
  the platform provides the store, connection settings in the env file otherwise, with a local compatible service for
  development.

## Required values

| What                 | Value                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| `files` table        | `id`, a unique `key`, `filename`, `contentType`, `size`, `createdAt`; with sign-in Authorization's `ownerId` |
| service              | `FilesService`, the only code touching the store's client or the `files` table                               |
| key                  | made by the server, unique                                                                                   |
| default content type | `application/octet-stream`                                                                                   |

## Conventions

- **File bytes live in the object store, metadata in the `files` table**; never contents in the database.
- **`FilesService` is the only code that touches either**, built by the server entry and reached through the app's
  context.
- **Upload stores the object, then the row, and deletes the object if the row fails**; delete removes the row, then the
  object.
- **Keys are generated by the server and unique**; a missing content type is `application/octet-stream`.
- **Upload and download endpoints authenticate**; a download sets `Content-Type` and `Content-Disposition`.

## Verify it is wired

- No table has a column holding file contents.
- Every upload path deletes the stored object when the metadata insert fails; a test covers that branch.
- Nothing but `FilesService` imports the store's client or the `files` table.
